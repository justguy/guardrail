# Guardrail Workflow Manifest Plan

Status: Historical implementation plan, feature shipped in MVP v1.0  
Audience: Claude or another coding agent reviewing or extending the implemented workflow-manifest feature  
Goal: Preserve the design and implementation intent behind first-class workflow manifests

## Objective

Extend Guardrail so one approved manifest can cover an explicit lifecycle such as:

1. start server
2. run project task
3. check status or health
4. apply approved fix path or abort path
5. restart server when required
6. verify again

This must preserve Guardrail's current honesty boundary:

- not a sandbox
- not a containment layer
- user remains responsible for approval
- Guardrail remains the source of truth for reusable approval
- any workflow change requires re-approval

## Why This Exists

The current MVP is built around:

- one normalized top-level command
- one approved manifest per exact command shape
- one supervisor launch per run

That is too narrow for the intended operational use case, where an agent must run a bounded lifecycle repeatedly without human hand-holding.

The extension should let Guardrail approve an explicit workflow, not force users to either:

- manage many per-command manifests, or
- hide the whole lifecycle behind one opaque wrapper script

## Resolved Design Decisions

These are deliberate decisions for the workflow-manifest feature.

1. Keep the current command-manifest behavior intact.
2. Add a second manifest kind instead of overloading the existing command manifest shape.
3. Use a human-authored workflow definition file plus a persisted approved workflow manifest.
4. Require every workflow step to be explicit up front.
5. Do not allow dynamic step creation at runtime.
6. Reuse the existing Guardrail command execution, validation, update, risk, and logging machinery per step where possible.
7. Add named service handles for long-running server processes.
8. Treat any change to steps, transitions, service references, trust/risk, or per-step command scope as drift.
9. Fail closed on unknown transitions, unknown services, or missing state.

## User-Facing Model

Guardrail should support two files:

- workflow definition: checked-in input authored by the user or team
- approved workflow manifest: persisted approval record generated by Guardrail

Example:

- definition: `workflows/server-cycle.json`
- approval record: `.guardrail/workflows/server-cycle.approved.json`

Interactive approval flow:

```text
guardrail workflow run --definition workflows/server-cycle.json --manifest .guardrail/workflows/server-cycle.approved.json
```

Non-interactive reuse:

```text
guardrail workflow run --definition workflows/server-cycle.json --non-interactive --approved-manifest .guardrail/workflows/server-cycle.approved.json
```

The definition is how the user expresses the lifecycle. The approved manifest is the reusable Guardrail approval record.

## Proposed CLI Surface

Add a new top-level subcommand instead of overloading `guardrail run`.

### Interactive

```text
guardrail workflow run --definition <path> --manifest <path>
```

### Non-Interactive

```text
guardrail workflow run --definition <path> --non-interactive --approved-manifest <path>
```

### Optional flags

- `--json`
- `--trust <class>`
- `--max-iterations <n>` only if this is part of the normalized workflow definition

Do not reuse `guardrail run` for workflow definitions. Keeping the command and workflow paths separate will make drift semantics and test coverage simpler.

## Workflow Manifest Schema

The approved manifest should be a normalized, hashable approval record derived from the workflow definition.

Example shape:

```json
{
  "version": 2,
  "tool": "guardrail",
  "kind": "workflow",
  "approvedAt": "ISO-8601 timestamp",
  "projectRoot": "/absolute/path",
  "workflowHash": "sha256-hex",
  "workflow": {
    "name": "server-cycle",
    "entryStep": "start_server",
    "maxIterations": 5,
    "services": [],
    "steps": []
  },
  "riskAssessment": {
    "trustClass": "reviewed_internal | pinned_external | generated | unknown",
    "riskLevel": "green | yellow | red",
    "reasons": ["string"],
    "requiresStrongConfirmation": true,
    "acknowledgedBy": "string | null",
    "acknowledgedAt": "ISO-8601 timestamp | null"
  }
}
```

Important rule:

- keep the existing command manifest schema unchanged
- add workflow manifests as `kind: "workflow"` with their own hash field

## Environment Policy

Both task step `run` blocks and service `start` blocks support an optional `envPolicy` field:

```json
{
  "envPolicy": {
    "inherit": true,
    "allow": ["PATH", "HOME"],
    "inject": { "MY_VAR": "value" }
  }
}
```

Semantics:

- `inherit: true` (default for workflow steps): the worker inherits the full parent environment. This differs from single-command mode, which defaults to `inherit: false`.
- `inherit: false`: the worker starts with an empty environment. Only vars named in `allow` are copied from the parent.
- `inject`: key-value pairs merged into the environment, overriding inherited or allowed values.
- `allow`: when `inherit: false`, only these var names are copied from the parent.

Risk evaluation:

- Vars matching known secret patterns (`secret`, `token`, `password`, `api_key`, `credential`, `auth`, `private_key`) in either `inject` keys or `allow` list trigger the `secret injection enabled` risk reason.
- Secret injection combined with shell mode or production-like targets escalates to `red`.
- The default `inherit: true` for workflow steps does not inflate per-step risk, since workflow steps inherently need the caller's environment. However, explicit `inject` with secrets is always flagged.

## Runtime Model

The workflow supervisor should behave like a bounded state machine.

### Step types for v1

- `task`
- `service_start`
- `service_stop`
- `service_restart`

That is enough for the intended lifecycle without introducing a huge DSL.

### Task step

A `task` step should reuse the current command-contract pipeline:

- normalize a per-step contract
- evaluate risk contribution
- launch with the current worker interface
- validate with the current validator module
- apply the existing update-policy checks if the step allows updates

### Service steps

Service steps should:

- launch a named background process
- store a service handle in workflow state
- reuse stop and restart rules declared in the workflow definition
- refuse unknown service IDs
- refuse restart of undeclared services

### Workflow state

Persist under `.guardrail/state.json`:

- current step ID
- iteration count
- named service handles
- prior step results
- convergence markers
- terminal reason when aborted

## Drift Model

Workflow drift should trigger re-approval for any of these changes:

- step added, removed, renamed, or reordered
- service added, removed, or changed
- transition target changed
- entry step changed
- `maxIterations` changed
- per-step command, args, cwd, mode, timeout, validator, or update source changed
- per-step scope changed
- trust class or workflow risk changed

Guardrail should render workflow drift in a readable form, for example:

```text
Workflow drift detected

Requested change:
+ Add step: restart_server
~ Step run_project args: ["33a69cb0"] -> ["44f19f10"]
~ Transition check_health.validation_failed: abort -> restart_server

This is outside your approved workflow contract.
Run halted. Re-run with explicit approval to widen scope.
```

## Risk Evaluation Model

Workflow risk should be derived from the highest-risk step plus workflow-level amplifiers.

Minimum workflow-level risk signals:

- any red step makes the workflow red
- service lifecycle capability raises risk at least to yellow
- patch or restart capability raises risk at least to yellow
- production-like targets or admin commands make the workflow red
- generated or unknown workflow provenance makes the workflow red

Store both:

- overall workflow risk
- step-level contributing reasons for debugging and approval UX

## Implementation Phases

## Phase 1: Add Workflow Definition Parsing

Goal:

- load, validate, and normalize workflow definitions

Files:

- `src/workflow.js`
- `src/contract.js`

Tasks:

1. Add a workflow-definition loader.
2. Resolve `projectRoot`, `cwd`, and step paths with `realpath`.
3. Validate unique step IDs and service IDs.
4. Validate that `entryStep` exists.
5. Validate that all transitions point to existing step IDs or terminal states.

Acceptance criteria:

- invalid references fail before approval
- duplicate step IDs fail before approval
- normalized definitions are deterministic

## Phase 2: Add Workflow Manifest Support

Goal:

- persist approved workflow manifests without breaking command manifests

Files:

- `src/manifest.js`
- `src/workflow.js`

Tasks:

1. Add `kind: "workflow"` manifest support.
2. Add stable workflow hashing.
3. Add workflow-aware manifest diffing.
4. Keep command-manifest behavior backward compatible.

Acceptance criteria:

- unchanged workflow definitions hash identically
- any step or transition drift changes the hash or diff set
- command manifests still load and compare correctly

3. Reuse the current trust-class model.
4. Produce readable reasons for approval screens and logs.

Acceptance criteria:

- a repo-local lifecycle with service restart evaluates at least to yellow

- workflow risk changes trigger re-approval

## Phase 5: Implement Workflow Supervisor

Goal:

- execute explicit workflow steps as a bounded state machine

Files:

- `src/workflow-supervisor.js`

Tasks:

2. Compare it against the approved workflow manifest.

Acceptance criteria:

- first run requires approval
- unchanged workflow reruns without prompting

## Acceptance Standard

The feature is done when all of these are true:

1. One approved workflow manifest can represent an explicit lifecycle with multiple named steps.
2. The agent can reuse that workflow non-interactively through Guardrail.
3. Any change to steps, transitions, services, risk, or per-step scope triggers re-approval.
4. Service restart behavior is explicit and bounded.
5. The implementation does not weaken the current command-manifest model.

## Stop Conditions

Claude should pause and ask for clarification if:

- the design starts turning into a general scheduler
- the workflow DSL starts requiring dynamic runtime command generation
- production-targeted workflow behavior needs stronger containment than Guardrail allows
- the implementation would require external dependencies
